# jev-snake

> 把贪吃蛇的「下一步往哪走」交给一个外部 LLM，然后量一量这件事到底成不成立。

这个目录是一条**测量台**：一个只画决策信息的界面，加上一把能跑分的尺子。
只保留能被跑通和被推翻的部分。完整记录在 [`FINDINGS.md`](./FINDINGS.md)。

## 动机

Jev（TypeSafe）不是一个聊天模型，它把问题设计成「给一份状态 + 一组问题，
拿回结构化答案」。这看起来天生适合游戏：不用解析自然语言，
不用正则抠 JSON，直接给几个选项让它选，还能白拿概率和置信度。

问题是**试完之后到底得到了什么结论**。所以这里重建一遍，
只为了能回答那个问题。

## 这个实验实际由四个断言组成

1. **协议可用**：`GameState` 序列化成 JSON 塞进 `state`，用一个 `choice`
   问题约束住选项（只能从合法方向里选），拿回
   `{choice, confidence, probabilities}`。
2. **幻觉可挡**：模型返回了我们**没问过**的方向时，不能执行它。
3. **引擎真的不知道决策者是谁**：同一份 `GameState`、同一个出口，
   常量策略 / 算法策略 / 模型策略可以互换，A/B 是公平的。
4. **代价可量**：一步决策要多久、烧多少 token、因此蛇能走多快。

## 跑起来

```bash
cd jev-snake

cargo test                 # 47 个测试，不需要 key、不需要外网

# 0. 打开界面看（默认接 Jev；没 key 也能配本地 mock 看）
cargo run -- play --source greedy --tps 6
cargo run -- play --source jev

# 1. 不接任何东西，纯看协议长什么样
cargo run -- protocol --tick 12

# 2. 拿两个不需要网络的决策源当尺子
cargo run -- bench --source constant --seeds 3
cargo run -- bench --source greedy   --seeds 5

# 3. 端到端：本地起一个假 TypeSafe，让模型源跑完整整一局
cargo run -- mock --latency-ms 400         # 终端 A：记下它打印的地址
no_proxy=127.0.0.1,localhost \
TYPESAFE_BASE_URL=http://127.0.0.1:PORT TYPESAFE_API_KEY=dummy \
  cargo run -- play --source jev                    # 终端 B：界面看
  # 或者不开界面，只要数字：
  no_proxy=127.0.0.1,localhost \
TYPESAFE_BASE_URL=http://127.0.0.1:PORT TYPESAFE_API_KEY=dummy \
    cargo run -- run --source jev --ticks 20 --trace

# 4. 真实调用（需要 key；直连会被 451 挡，所以要代理）
https_proxy=http://127.0.0.1:7897 \
TYPESAFE_API_KEY=apikey_xxx cargo run -- run --source jev --ticks 20 --trace

# 5. 实验开关（都写在这里，随时能打倒结论）
JEV_PROMPT_LANG=zh JEV_STATE_KIND=string \
  cargo run -- run --source jev --ticks 30 --seed 1   # 2×2 对照的一格

JEV_PLAN=3 cargo run -- run --source jev --ticks 20     # 一次问 3 步

TYPESAFE_RETRIES=0 cargo run -- run --source jev        # 关掉重试，看抖动有多疼

cargo run -- run --source jev --dump /tmp/dec.json     # 逐条决策记录落盘
```

`run` / `bench` 跑完会打一张**概率探针表**：把 confidence 按 0.0~0.9 切档，
看每一档里撞死的比例有没有随阈值下降。门控有没有用，看这张表就够了。

### 代理

`https_proxy` / `https_proxy` / `all_proxy`（大小写都认）、`no_proxy` 都会读。
支持 `http://`（CONNECT 隧道）和 `socks5://` / `socks5h://`，带用户名密码也行。
优先级和 curl 一致：`<scheme>_proxy` > `all_proxy`，`no_proxy` 命中就直连。

**注意本地 mock 要显式绕开** —— 和 curl / Go / Python 一样，这里不会偷偷
跳过 loopback，所以跑 mock 时记得带上 `no_proxy=127.0.0.1,localhost`。
`cargo test` 里的用例都把代理钉死成 `Direct`，不受环境影响。

不支持 `https://` 开头的代理（到代理本身走 TLS）—— 遇到会直接报错，
而不是静默降级成明文 CONNECT。细节见 `src/proxy.rs` 的模块文档。

`--json` 可以把所有汇总换成 JSON 输出。`bench --seeds N` 跑多个 seed，
回答的是「稳不稳」而不是「这一局多高」。

> `cargo test` 里的 8 条端到端用例会在 `127.0.0.1` 上起一个随机端口的
> mock 服务。它们**不连外网**，但需要能 bind 本地端口 ——
> 被沙箱或严格防火墙挡住时会看到 `PermissionDenied`，那是环境问题，不是代码问题。

```
│ 决策 128 · 错误 0 · p50 1204ms · p95 1310ms · token in 16384 / out 1024 │

╰──────────────────────────────────────────────────────────────────────╯
```

四个区块都在回答同一个问题：**模型每一步在想什么，代价是什么。**
所以界面上没有分数排行榜、没有连击特效 —— 只有方向、置信度、
概率分布、延迟，和一张流水表。

**请求在飞的时候界面不会冻住**，右上角写着「等待模型…」。这是刻意的：
往返时间恰恰是这条实验最该被看见的东西，如果屏幕在等待期间卡死，
就等于把要观察的现象藏起来了。

### 按键

| 键 | 作用 |
|---|---|
| `空格` | 暂停 / 继续 |
| `r` | 同 seed 重开（可复现） |
| `n` | 换个 seed 重开 |
| `+` / `-` | 调速，**只对本地决策源有效** |
| `q` / `Esc` / `Ctrl-C` | 退出 |

模型源下调速键被去掉了：那种情况下节奏由 API 决定，假装能加速
就是骗人。界面右上角一直写着当前是哪种节奏。

## 实测结果（2026-10-17，macOS，24×12 棋盘）

| 决策源 | 平均得分 | 每步延迟 p50 | token/步 | 一局耗时 |
|---|---|---|---|---|
| `constant`（能右就右） | 0.3 | 0 ms | 0 | < 1 ms |
| `greedy`（洪水填充 + 贪心） | 15.8 | 0 ms | 0 | ~5 ms |
| `jev`（真实 API，走代理） | 1（24 步截断） | **839 ms** | 输入 500 / 输出 35 | 20.8 s |

模型源那一行还远不如 `greedy`，但**它吃到食物了**，而且是它自己走的：

```
 tick  得分  蛇头      食物      方向     延迟    置信度
     2    0  ( 6, 4)  ( 3, 0)  up      1132ms   0.46
     5    0  ( 6, 1)  ( 3, 0)  left      804ms   0.27
     8    0  ( 3, 1)  ( 3, 0)  up        846ms   0.58
     9    1  ( 3, 0)  (15, 7)  right     1039ms   0.98   ← 吃到
    15    1  ( 9, 0)  (15, 7)  right      847ms   0.32
    21    1  (15, 0)  (15, 7)  down       819ms   0.34
```

注意置信度：吃到食物那一步是 0.98，但通往它的好几步只有 0.27~0.32，
后面朝着第二个食物走的十几步甚至掉到 **0.14**。

（下面是 24 步一小段的印象，样本不够；120 步的正式分析见下。）

### 120 步真实数据：confidence 到底有没有信息量

`run --dump <path>` 会把每一次决策的原始记录写下来（方向、confidence、
完整概率分布、这一步是否吃食、是否致命）。拿 120 步真实决策跑：

| | 步数 | 吃到食物 |
|---|---|---|
| `confidence ≥ 0.5` | 73 | 9 步（**12.3%**） |
| `confidence < 0.5` | 46 | 1 步（**2.2%**） |

**confidence 确实带信息 —— 差 5.6 倍**，而且方向是「高置信度对应吃到东西」。
这条推翻了第一轮那个「置信度和正确率脱节」的印象：那 24 步样本太小。

另外两件值得记下来的：

- **模型永远选概率最大的那个选项**（119/119）。所以 `probabilities` 不是一个
  独立的决策信号，它是模型内部状态的**读数**。有信息的是那个分布本身。
- 模型比想象的**更确定**：选中的方向拿到中位数 0.73 的概率，90 分位是 1.00。
- 这批 120 步里**一局都没死**，所以「confidence 能不能预测撞死」**没测到**。

### 网络会抖，而抖动比决策本身更容易毁掉实验

走代理实测：**20~37% 的请求在传输层就失败了**
（`TLS 握手失败：the handshake process was interrupted`）。

这件事一开始伪装成了结论。第一轮跑 2×2 时 `zh` 全是 0 分、`ticks=1`，
看起来像「中文提问有多差」—— 真相只是**第一次抖动就把整局掐断了**。

所以客户端现在只对**传输层**的错误重试（`Network` / `Timeout`；
`Http` 是服务端的回答，`Invalid` 是自己解析不出来，重试都没意义），
次数由 `TYPESAFE_RETRIES` 控制，默认 1，**并且重试次数会被统计上报** ——
延迟统计因此含了重试，这是实测的诚实代价，不藏。

开了 3 次重试之后，20 局实验里总共只有 2 局出现过 1 次失败。

### 那句 451 是地区拦截，不是 API 改动

```
POST https://api.typesafe.ai/v1/systemone
→ HTTP 451 {"title":"Typesafe is not available in your region.","status":451}
```

和当前文档逐字段核对过（2026-10-17 抓的 `docs.typesafe.ai/api`）：
端点、`Authorization: Bearer`、`model` 别名、choice 的 `type` / `instructions` /
`criteria`、响应的 `model` / `answers` / `usage` —— **一个字段都没变**。

451 是在一层前置的地理网关上返回的，连请求体都不校验：

| 探测 | 实际 | 若是 API 层该回 |
|---|---|---|
| 非法 JSON `this is not json {{{` | 451 | 400 |
| 不存在的路径 | 451 | 404 |
| 完全不带 key | 451 | 401 |

所以「API 改了导致用不了」这个因果链不成立：任何 API 改动在这个网络环境下
**都不可能被观测到**。而走 `127.0.0.1:7897` 代理时，同一个请求回的是 **200**。

### 代价：一次决策 = 一次网络往返 = 蛇的一步

剩下的核心问题不是「能不能选对方向」，而是这个：

> **一次决策 = 一次网络往返 = 蛇的一步。**

模型往返 839ms，蛇就只能每秒走 1.2 格。
引擎在模型模式下只等决策、不自己走，所以**游戏速度完全由 API 决定**，
跟界面上的调速键没关系 —— 那几个档位对模型源是假的，界面右上角一直写着这一点。

这不是 bug，是「用 LLM 当决策器」这个结构的固有成本：
决策的分辨率被网络的分辨率锁死了。本项目把它量化出来：
`run --source jev --json` 里的 `decisions_per_sec` 就是蛇的理论最快速度。

同一台机器上 `greedy` 跑完一局只要 42 ms。模型源比算法源慢四个数量级，
而当前分数还不如它 —— 这是这条实验目前最扎人的一条结论。

### 2×2 对照：到底是语言，还是 state 编码？

上一节说「改用英文提问 + state 传对象」之后模型会寻路了 —— 但那是**两处同时**改的。
所以做了个 2×2：每格 5 个 seed、每局 30 步，共 20 局真实调用。

```
                      state=对象   state=字符串
   英文提问               2.20         1.80
   中文提问               0.20         0.60
   ----------------------------------------------
   编码边际               1.20         1.20

   语言边际：英文 2.00 vs 中文 0.40    差 +1.60   <- 主因
   编码边际：对象 1.20 vs 字符串 1.20  差 +0.00   <- 没有影响
```

**是语言，不是编码。** 双重编码那个改动纯属误打误撞 —— 它一点用都没有。

每格的得分：`en+object [2,2,2,2,3]`、`en+string [2,2,2,0,3]`、
`zh+object [1,0,0,0,0]`、`zh+string [1,0,2,0,0]`。

这和文档的说法完全一致：「Jev 的主语言是英语，CJK 也能接受但准确率更低」。
**拿 Jev 做任何正经的事之前，先把提问写成英文。**

复现：

```bash
for lang in en zh; do for kind in object string; do for seed in 1 2 3 4 5; do
  JEV_PROMPT_LANG=$lang JEV_STATE_KIND=$kind \
    cargo run -- run --source jev --ticks 30 --seed $seed --on-error continue --json
done; done; done
```

### 一次问 N 步：能省往返，但省不下来

`JEV_PLAN=3` 把问题从「下一步往哪走」换成「这 3 步按什么顺序走」
（候选路线 = 不含 180 度掉头的长度 3 序列），拿回路线后**本地一步步验着走**，
只有下一步在当前棋盘上不再合法时才重新问。

同一局（seed 1，20 步）：

```
              网络往返   每往返换几格   重试   墙钟
   JEV_PLAN=1      20         1.00       0    26.9 s
   JEV_PLAN=3       7         2.86       5    24.6 s
```

**往返数少了 65%，墙钟几乎没变。** 因为这局 `plan=3` 撞上了 5 次重试，
而失败的握手要等好几秒才报错 —— 省下的往返被失败吃掉了。

换一个**没碰上重试**的局（seed 42，12 步，0 重试）再看：

```
   JEV_PLAN=3   4 次往返   4.5 s   每秒 2.6 格
   JEV_PLAN=1  12 次往返  10.8 s   每秒 1.1 格
```

**网络干净的时候，规划实打实地快 2.4 倍。** 上一张表里看不到效果，
纯粹是那 5 次重试把优化全吃掉了 —— 不是优化没用，是被噪声淹了。

结论：**两个都要。** 规划确实有效，但**先修网络**，否则测不出它有没有效。

## 代码地图

```
jev-snake/
├── src/
│   ├── game.rs       引擎。只认识 Direction，不认识决策者。
│   │                 legal_directions() 是「什么方向合法」的唯一定义。
│   ├── jev.rs        协议。GameState -> JSON -> POST /v1/systemone -> Decision。
│   │                 也管 chunked 解码、传输层重试、单步/多步两种提问。
│   ├── proxy.rs      代理隧道。HTTP CONNECT / SOCKS5 —— 直连 451，代理 200。
│   ├── provider.rs   三个决策源（constant / greedy / jev），同一个 trait。
│   ├── mock.rs       本地假 TypeSafe：能回幻觉、451、垃圾。
│   ├── ui.rs          界面。一个纯函数 render(frame, state)，没有 I/O。
│   ├── app.rs        事件循环。模型决策丢后台线程，界面不冻。
│   └── main.rs       CLI：play / run / bench / protocol / mock
└── tests/end_to_end.rs  8 条端到端测试，每次 cargo test 都跑
```

依赖方向：`app` 依赖 `ui` / `provider` / `game` / `jev`，
`provider` 依赖 `game` 和 `jev`，`ui` 只依赖 `game` 的类型
（读状态、画格子，不认识引擎），`game` 谁都不依赖。

界面是**纯函数**，所以能在没有终端的情况下测：渲染一屏，逐格读缓冲区，
断言蛇头在不在、概率条对不对、451 有没有显示出来、排版有没有坏。
这里的测法是**渲染成缓冲区后逐格断言** —— 不是截图对比，是读字符确认
「蛇头在不在」「概率条对不对」「451 有没有显示出来」。

## 边界：这个项目刻意不做什么

| 不做 | 为什么 |
|---|---|
| 主题 / 像素 logo / 中英双语 | 和「量决策」无关。装饰性内容是牢笼的一部分 |
| 排行榜 / 连击特效 | 同上。界面只回答「模型每步在想什么、代价是什么」 |
| 调速档位（模型源） | 对模型源是假的 —— 节奏由 API 决定，假装能加速就是骗人 |
| Chat / OpenAI 兼容层 | `/v1/systemone` 根本不吃 chat 消息，留着会误导下一个人 |
| 子进程 bot 协议 | 另一条实验，与这个无关 |

被砍掉的东西和理由，逐条写在 [`FINDINGS.md`](./FINDINGS.md)。

## 遗留问题

- **一次决策 = 839ms，贪吃蛇只需要每秒 1~3 格。** 这是硬成本，优化提示词
  压不动它。值得试的三条路：一次请求问 N 步（把 lookahead
  打包进一次往返）、缓存相似局面、或者只让模型在**分叉点**决策
  （直道部分交给本地算法）。第三种最可能把「每秒 3 格」变成
  「每秒 8 格 + 每 5 步问一次模型」。
  **第一条（`JEV_PLAN=N`）已经实现并测过了**，见上：能省 65% 往返，
  但在会抖的网络上换不来墙钟时间。缓存和分叉点这两条没试。
- **`confidence` 能不能预测「撞死」？** 已知它能预测「吃到食物」
  （高置信度 12.3% vs 低置信度 2.2%），但那 120 步里一局都没死，
  **所以「预测死亡」根本没被测到**。要回答得先跑几局会死的。
- **`probabilities` 的形状。** 已确认模型永远选最大概率那个（119/119），
  所以它是读数不是信号。但分布本身还值不值得用，没测。
- **语言 vs 编码已经做了 A/B**，答案是「只和语言有关，和编码无关」，见上。
- **多跑几个 seed。** 2×2 每格只有 5 局。5 个 seed 证不了「稳」，
  只能证「不是偶然」。
